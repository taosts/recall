下面是我们这轮讨论的开发前总结，可以作为项目初始文档/README 草稿的思想基础。

# 项目问题来源

最初的问题来自浏览器书签管理体验：

用户在 Edge/Chrome 收藏了大量网站后，经常出现：

> 我知道我收藏过、看过、研究过某个东西，但我忘了它叫什么、放在哪、当时为什么收藏。

传统书签系统基于：

```text
文件夹
标题
URL
标签
```

但人的记忆通常不是这样工作的。

人更常记得：

```text
大概什么时候看的
当时在研究什么问题
页面长什么样
它和哪些内容一起出现过
我当时为什么觉得它重要
我最后有没有采用这个方案
```

因此，真正的问题不是“书签太多”，而是：

> 用户无法通过模糊记忆找回自己曾经接触过的信息。

---

# 核心洞察

## 1. 现有工具保存的是信息，不是经历

浏览器保存 URL、标题、文件夹。

笔记软件保存文本。

Git 保存代码变化。

但它们通常不保存：

```text
我当时在解决什么问题？
我为什么打开这个页面？
我为什么收藏它？
我排除了哪些错误方向？
我最终为什么相信这个方案？
```

也就是说，信息还在，但探索过程丢失了。

---

## 2. 人记住的是任务，不是网页

浏览器认为用户访问的是：

```text
网页 A
网页 B
网页 C
```

但用户脑中真正对应的是：

```text
研究 OpenWrt
搭建 NAS
排查实验室电脑卡顿
学习某个框架
解决某个 bug
```

网页只是任务过程中的痕迹。

所以项目的核心对象不应该只是 `Bookmark`，而应该更接近：

```text
Quest / Journey / Investigation
```

即一次探索任务。

---

## 3. 用户真正的查询语言是“模糊记忆”

用户脑子里的查询往往是：

```text
去年冬天研究 NAS 时看过的那个 ZFS 缓存文章
```

或者：

```text
我记得有一张蓝色网络拓扑图
```

或者：

```text
当时我为了解决实验室硬盘占用 100% 找到过一个方案
```

但浏览器只允许用户搜索：

```text
zfs cache
openwrt dns
disk 100%
```

用户被迫把记忆翻译成关键词。

这个项目要做的是支持用户直接用“记忆线索”检索。

---

## 4. 搜索不是最终目的，触发记忆才是

传统搜索的目标是返回结果。

但这个项目的目标应该是：

> 让用户想起来。

例如用户搜索：

```text
我当时研究旁路由时看到过的 DNS 工具
```

理想返回不只是网页列表，而是：

```text
这可能是你在“OpenWrt 旁路由配置”任务中看到的内容。

当时你还看过：
- WireGuard
- DNSMasq
- AdGuard Home
- OpenWrt 防火墙配置
```

用户看到这些上下文后，可能会瞬间恢复记忆。

所以项目不是普通搜索引擎，而是：

> Memory Trigger System
> 记忆触发系统

---

## 5. 连锁记忆/探索过程是更高价值点

我们进一步讨论到，真正有价值的不只是找回最终网页，而是找回：

```text
我是怎么一步步找到它的？
我当时踩过哪些坑？
我为什么排除了其他方案？
我为什么最后选择这个方案？
```

这可以称为：

```text
Research Replay
Thinking Replay
Decision Archaeology
```

即重现探索过程/思维路径/决策考古。

这比书签管理器更有差异化。

---

# 项目定位

不建议把项目定位为：

```text
书签管理器
```

也不建议一开始定位为：

```text
AI 知识库
```

更准确的定位是：

> 一个本地优先的个人记忆触发系统，用于帮助用户通过模糊记忆找回曾经接触过的信息，并逐步重建当时的探索过程。

一句话版本：

> 帮助用户想起自己当时是怎么找到答案的。

---

# 隐私原则

这个项目触碰的数据非常敏感：

```text
浏览历史
搜索历史
收藏记录
页面停留时间
复制行为
下载行为
阅读轨迹
```

这些本质上是用户的认知活动记录。

所以隐私不是附属功能，而是项目生死线。

建议从第一天就确立原则：

```text
Local First
默认本地存储
默认离线可用
不上传浏览历史
不强制云账号
AI 可选
本地模型优先
用户可完全删除数据
```

不建议第一版做：

```text
持续截图
全屏 OCR
自动上传 AI 分析
云端同步
```

因为这会迅速让项目变成隐私噩梦。

# 可选路线

我们讨论过几条路线。

## 路线 A：记忆锚点 Memory Anchors

不记录全部过程，只记录关键节点。

可能的锚点包括：

```text
收藏
下载
长时间停留
复制文本
搜索关键词
用户主动标记
关闭大量标签后保留的页面
```

优点：

```text
数据量小
隐私压力低
可解释性强
容易做 MVP
```

这是最适合起步的方向。

---

## 路线 B：探索任务 Quest

把一组相关行为聚合成一次任务。

例如：

```text
任务：研究 ZFS 缓存
包含：
- 搜索词
- 访问页面
- 收藏网页
- 下载 PDF
- 用户备注
- 最终结论
```

这是项目的核心差异化方向，但第一版可以先弱化实现。

---

## 路线 C：时间机器

用户可以按时间回忆：

```text
去年冬天
上个月
某个项目开发期间
某次课程/实验/工作任务期间
```

适合解决：

> 我记得大概是那个时间段看过。

---

## 路线 D：思维地图

系统根据长期记录生成主题关联图：

```text
OpenWrt
├── DNS
├── WireGuard
├── NAS
└── 防火墙
```

这是后期方向，不适合第一版直接做。

---

## 路线 E：决策日志

收藏或标记时，让用户用极低成本记录：

```text
为什么保存？
这个页面解决了什么？
这个方案是否失败？
```

例如：

```text
ZFS tuning guide

备注：
用于排查 NAS 内存占用问题，后来发现 ARC 不是主要瓶颈。
```

价值很高，但不能要求用户每次都写，否则会变成又一个笔记软件。

---

# MVP 建议

第一版不要做太大。

不要一开始做：

```text
AI 自动总结
完整思维链重建
截图识别
全量浏览历史分析
复杂知识图谱
云同步
```

第一版目标应该非常小：

> 给用户一段模糊记忆，能否比 Chrome/Edge 更快地找回目标信息？

例如支持查询：

```text
去年研究 NAS 时看过的 ZFS 缓存文章
```

```text
我收藏过一个讲 OpenWrt DNS 的网页
```

```text
有一篇关于 Docker 网络的英文长文
```

如果能找出来，并让用户觉得：

```text
对，就是这个。
```

MVP 就成立了。

# 第一版数据源建议

建议从低隐私风险、高可用数据开始：

```text
浏览器书签
浏览器历史
搜索历史
收藏时间
页面标题
URL
域名
访问时间
访问次数
```

暂时不建议第一版做截图。

可以后续再考虑：

```text
网页正文快照
页面截图
用户备注
下载文件
GitHub Stars
本地文档
ChatGPT 对话
```

# Quest 识别思路

探索任务可以通过几类信号推断。

## 1. 时间聚类

短时间内连续访问的一组页面，很可能属于同一任务。

## 2. 搜索词聚类

连续搜索：

```text
zfs cache
zfs arc
zfs memory
truenas zfs tuning
```

大概率属于同一主题。

## 3. 内容聚类

页面标题、域名、正文关键词相似，可以归为一组。

## 4. 行为锚点

收藏、下载、复制、长时间停留，说明该节点更重要。

## 5. 用户微调

系统自动推断，用户只做轻量修正：

```text
合并任务
拆分任务
重命名任务
标记重要
添加一句备注
```

理想比例：

```text
80% 被动记录
20% 主动修正
```

# AI 的位置

AI 不应该是第一版核心。

第一版可以先用：

```text
SQLite FTS5
BM25
关键词提取
时间过滤
简单聚类
```

先验证需求。

AI 可以在第二阶段作为“记忆查询解释器”。

例如用户输入：

```text
去年冬天研究 NAS 时看过的 ZFS 缓存文章
```

AI 解析为：

```text
时间范围：去年冬天
主题：NAS
关键词：ZFS, cache, ARC
意图：找网页/文章
```

然后交给本地检索系统查询。

AI 是解释器，不是数据拥有者，也不是唯一核心。

# 推荐技术路线

如果你单人开发，建议：

```text
浏览器扩展：TypeScript
本地数据库：SQLite + FTS5
本地服务：Go / Rust / Node.js
桌面端：Tauri
前端 UI：React / Vue / Svelte 均可
```

更轻量的 MVP：

```text
先做浏览器扩展 + 本地 IndexedDB
后续再抽离本地服务
```

但如果你想长期做成 Local First 桌面产品：

```text
Tauri + SQLite
```

会更稳。

# 第一阶段功能清单

建议第一阶段只做这些：

```text
1. 导入 Edge/Chrome 书签
2. 导入最近 N 天浏览历史
3. 建立本地全文索引
4. 支持自然语言/模糊描述搜索
5. 支持按时间过滤
6. 显示结果上下文
7. 显示“当时附近还看过什么”
8. 用户可以给结果加一句备注
```

关键功能不是“返回网页”，而是：

```text
显示上下文
```

例如：

```text
你在 2025-12-03 晚上访问过这个页面。
前后你还搜索/访问了：
- openwrt dnsmasq
- adguard home
- wireguard route
```

这会更容易触发记忆。

---

# 项目最小验证问题

你现在最该验证的不是技术能不能做，而是：

> 用户输入模糊记忆时，系统能不能返回足够能触发回忆的结果？

测试样例可以是：

```text
我去年看过一个讲 ZFS 缓存的网页
```

```text
我记得有个 Docker 网络教程，里面讲 bridge
```

```text
我当时为了解决磁盘 100% 的问题查过资料
```

```text
之前收藏过一个 OpenWrt 旁路由配置教程
```

```text
有个英文页面讲 GitHub Actions 缓存优化
```

如果这些查询能明显优于浏览器自带历史/书签搜索，就说明方向正确。

---

# 项目的边界

第一版要避免变成：

```text
另一个书签管理器
另一个笔记软件
另一个知识库
另一个 AI 套壳
另一个浏览器历史查看器
```

它的边界应该是：

> 我不帮你整理所有知识，我帮你找回曾经接触过的信息和当时的上下文。

---

# 一句话总结

这个项目不是从“管理书签”出发，而是从一个更深的问题出发：

> 在信息爆炸和 vibe coding 的背景下，人接触信息的速度越来越快，但回忆和追溯能力没有同步增强。

因此，这个项目要解决的是：

```text
我知道我见过
但我想不起来在哪里
也想不起来当时为什么觉得它重要
```

最终目标可以是：

> 构建一个本地优先的个人记忆触发系统，帮助用户通过模糊记忆找回信息，并逐步重建自己的探索过程。
